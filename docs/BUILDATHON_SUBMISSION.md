# PayTwin OS — Razorpay Buildathon Submission

## Track

**Track 03 — AI Revenue Recovery.** PayTwin detects payment revenue at risk,
diagnoses the affected cohort, compares bounded recovery actions, enforces
deterministic safety policies, and measures a treatment/control recovery batch.

## What a reviewer can verify

1. Run make bench to regenerate fixed-seed model, detection, RCA, and
   revenue-at-risk evidence.
2. Run make demo to train and validate the success model, build the local
   recovery batch, and exercise the end-to-end path.
3. Run make test for the regression suite, including the assertion that a
   validated model scores incident payments and contributes to candidate ranking.
4. Run make razorpay-demo to exercise the credential-free,
   Razorpay-shaped local lifecycle: order, signed webhook, Checkout proof,
   one fulfilment, refund, duplicate and forged-callback controls.

## Evidence boundary

- All benchmark and recovery figures are synthetic, fixed-seed local test
  evidence. They are deliberately not described as merchant-production results.
- The success model is LogisticRegression plus isotonic calibration. It is
  trained reproducibly during the demo, accepted only after its documented
  held-out gates pass, and is then used to score each failed incident payment.
- The model informs candidate ranking only. It cannot authorize a customer
  contact, route change, retry, or payment action; deterministic policy and
  approval controls retain that authority.
- The Razorpay surface is a local, provider-shaped test harness. It makes no
  Razorpay API call and uses no Razorpay account credentials.

## Judge walkthrough

1. Start on the Model Health page: the model registry exposes the actual
   LogisticRegression plus isotonic model and fixed-seed evidence.
2. Trigger the local scenario, open the War Room, and inspect the candidate
   card. It shows the validated model version and the cohort success propensity.
3. Review the policy decision and audit trail. The model can rank, but it
   cannot bypass policy, consent, caps, approval, idempotency, or stopping rules.
4. Open the local Razorpay Test Mode surface to verify the modeled lifecycle
   boundary and fault controls.
